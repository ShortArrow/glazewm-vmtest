# アーキテクチャ

用語はdocs/PRD.jp.mdの「用語」に従う。

## 構成

```
┌───────────────────────────────────────────────────┐
│ Domain                                            │
│   Topology, WindowKind, Scenario, Step,           │
│   Invariant, Baseline, Verdict                    │
├───────────────────────────────────────────────────┤
│ Application                                       │
│   ScenarioRunner, SutBuilder, ArtifactStore       │
│   Ports: Hypervisor, DisplayController,           │
│          SessionController, WorkloadController,   │
│          InputController, GuestExecutor, Observer │
├───────────────────────────────────────────────────┤
│ Adapters                                          │
│   hyperv / dockur-windows / rdp-client /          │
│   vnc-client / guest-daemon                        │
└───────────────────────────────────────────────────┘
```

依存は下から上への一方向。Domainは仮想化基盤もSUTの実装も知らない。

### Domain

- `Topology`: ディスプレイの集合を持つ値オブジェクト。ディスプレイごとに識別子、矩形、作業領域、DPI、プライマリかどうかを持つ。
- `WindowKind`: docs/PRD.jp.mdの「ウィンドウの種類」の各軸から1つずつ値を取ったもの。
- `Scenario`: Given（初期`Topology`、SUTの設定）、When（`Step`の列）、Then（`Invariant`の集合と、必要なら`Baseline`）。
- `Step`: モニター追加、モニター削除、設定変更、RDP接続/切断、VNC接続/切断、スリープ/復帰、画面オフ/復帰、ロック/アンロック、負荷の開始/停止、ウィンドウの生成、ウィンドウの応答停止/再開、SUT設定の差し替えと再読み込み、待機。
- `Invariant`: 観測結果を受け取り、合否と差分を返す純粋関数。
- `Baseline`: シナリオの基準実行で記録した正規化済みの観測結果と、そのSUTのコミット。
- `Verdict`: ステップごとの判定結果。不変条件の違反、ベースラインからの逸脱、落ち着かなかった、skipを区別して持つ。

### Application

`ScenarioRunner`は次の順に実行する。

1. `Hypervisor`でゲストをスナップショットから復元し、ゲストデーモンが準備完了を報告するまで待つ。
2. Givenのトポロジーを`DisplayController`で適用し、GivenのSUT設定を`GuestExecutor`で配置する。
3. `SutBuilder`がホストでSUTをビルドし、`GuestExecutor`が配置し、ゲストデーモンが起動する。
4. 落ち着くまで待ってから`Observer`で観測する。これをステップ0の観測とする。
5. Whenの各`Step`について、対応するポートで実行し、落ち着くまで待って観測し、`Invariant`を判定する。さらに、観測結果を新しい`Baseline`に記録するか、既存の`Baseline`と比べる。
6. ログ、状態ダンプ、スクリーンショット、実行した操作列を`ArtifactStore`に保存する。

記録した操作列は、シナリオのWhenとしてランナーに渡し直せる。失敗した実行はこの方法で再実行する。シードからWhenの操作列を作る生成器もある。

各ポートの責務は次のとおり。

| ポート | 責務 |
|---|---|
| `Hypervisor` | 起動、停止、スナップショットの作成と復元 |
| `DisplayController` | ゲストのトポロジーをモニター単位で変更する。Win+Pと同じく、ゲストのOSが使うディスプレイを切り替える |
| `SessionController` | RDP/VNCクライアントの接続と切断、ロックとアンロック、スリープと復帰 |
| `WorkloadController` | CPU/メモリ/GPU負荷の開始と停止。テスト用ウィンドウの生成、応答停止、再開、破棄 |
| `InputController` | ユーザーと同じ入力をゲストに与える。テスト用ウィンドウを、メッセージを処理しているかどうかにかかわらずクリックする |
| `GuestExecutor` | ゲストへのファイル転送と、ゲストデーモンへの要求の送信。デーモンはゲスト内のTCPで待ち受け、1行に1つのJSONでやり取りする。デーモンには認証がなく、glazewmにコマンドを実行させられるので、そのポートはどのネットワークからも届かないようにする。SSHのポート転送か、ホストのループバックに公開したポートを通してつなぐ |
| `Observer` | トポロジー、ウィンドウの矩形、glazewmの状態、zebarのウィンドウ配置、プロセスの生存、IPCの応答、スクリーンショットの取得 |

### Adapters

仮想化基盤ごとに、`Hypervisor`、`DisplayController`、`SessionController`と、`Observer`のうちスクリーンショットの部分を実装する。
Hyper-Vの`Hypervisor`は、WMIだけを使ってゲストの電源を切り、ゲストを止めて取ったチェックポイントに戻して起動する。PowerShellはHyper-Vのホストで実行する。実行の場所は、ランナーのマシンか、SSHでつないだホストである。そのため、ランナーはHyper-Vのホストでも、ホストとゲストに届く別のマシンでも動く。動いているゲストのチェックポイントなら、約13秒ではなく約4秒で戻る。しかし、そのチェックポイントには取ったときに動いていたゲストデーモンが入っており、ランナーのものより古いゲストデーモンが動いていても気づけない。止めたゲストのチェックポイントなら、実行のたびに配置したゲストデーモンが使われる。ゲストのSSHにはネットワーク上のアドレスでつなぎ、ゲストのループバックで待ち受けるゲストデーモンにはSSHのポート転送でつなぐ。
`GuestExecutor`、`WorkloadController`、`InputController`と、`Observer`の残りの部分はゲストデーモンを経由するので、全Windowsゲストで共通になる。負荷は、デーモンが負荷の種類ごとに起動して終了させる別の負荷生成プロセスが作る。こうすることで、デーモン自身はほかのプロセスと同じだけ応答できる。負荷生成プロセスはデーモンと一緒に配置する。CPU負荷は、すべての論理プロセッサを100ミリ秒ごとに指定の割合だけ使う。メモリ負荷は、物理メモリの指定の割合を確保し、その全ページに毎秒書き込む。GPU負荷は、物理GPUなしでのGPU負荷のスパイクを待つ。

ゲストデーモンは自動ログオンするユーザーの対話セッションで動く。ランナーはスナップショットを復元するたびに最新のデーモンのバイナリを配置し、ゲストイメージに登録したスケジュールタスク（docs/GUEST-IMAGE.jp.md）で起動する。そのため、デーモンを変えてもゲストイメージを作り直す必要はない。SUTとテスト用ウィンドウの起動、負荷の発生、トポロジーとウィンドウの矩形の読み取りを、そのセッションの中で行う。glazewmとテスト用ウィンドウは、`RunLevel Limited`のスケジュールタスクで動くデーモンの子プロセスとして、そのセッションでユーザーの整合性レベルで動く。zebarも同じ整合性レベルで動く。zebarは、glazewmのサンプルの設定と同じくglazewmが起動時のコマンドで起動するか、シナリオがzebarの標準エラー出力を残す必要があるときはデーモンが起動する。昇格したテスト用ウィンドウは、対話ログオン種別で`RunLevel Highest`のスケジュールタスクで起動する。ゲストイメージは利用者のマシンと同じくUACを有効にしておく。UACが無効だとすべてのプロセスが昇格して動き、ウィンドウの種類の「権限」の軸を区別できない。
テスト用ウィンドウは、UIフレームワークごとに1つあるテスト用ウィンドウのアプリケーションが作る。各アプリケーションはそのフレームワーク本来の言語で書く。ランナーはスナップショットを復元するたびに、各アプリケーションをゲストデーモンと一緒に配置する。アプリケーションが必要とするランタイムはゲストイメージに入れる。どのアプリケーションも、デーモンへのループバック接続で同じ制御プロトコル（生成、応答停止、再開、破棄。ウィンドウの種類の他の軸は引数で渡す）を受け付ける（docs/ADR/004-test-window-application-transport.jp.md）。そのため、フレームワークを足すときはアプリケーションを1つ足すだけで、ランナーは変わらない。デーモンは、上限を超える数のテスト用ウィンドウや、上限より長い時間の幅を求める要求を断る。こうすることで、1つの要求がデーモンをいつまでも占有しないようにする。上限は要求からではなく、ランナーがデーモンの隣に配置するファイルから読み、既定は500個と60秒とする。起動したアプリケーションが接続してくるまで待つ時間も同じファイルで決め、既定は3秒とする。時間内に接続しなければ、その要求は失敗になる。アプリケーションは、ウィンドウができてフォアグラウンドになってから生成に答える。こうすることで、続けて生成したウィンドウが毎回同じように配置される。

基盤上で、または現在のセッション状態で実行できない操作（例: RDPセッションが画面を持っている間のモニター単位の変更）は、アダプターが未対応として返し、そのステップはskipとして報告する。全ステップがskipになったシナリオは「実行されなかった」として報告する。

## 設計意図

### 判定は落ち着いた状態に対して、不変条件とベースラインで行う

オラクルは、期待値のスクリーンショットではなく観測結果で判定する。
スクリーンショットは解像度、フォント、テーマ、タイミングで変わり、ピクセルの差分からは原因を指せない。
スクリーンショットは失敗の調査用に成果物として残すだけにする。

観測はゲストが落ち着いてから行う。待機時間はzebarのモニター検出の周期以上にする。zebarはウィンドウメッセージではなく、4秒ごとのポーリングでモニターの変化を検出するためである。落ち着くのを待つ代わりに固定時間スリープすると競合が隠れるので、制限時間内に落ち着かなかったステップは「落ち着かなかった」として報告する。

不変条件は、SUTが何をすべきかに関わらず成り立つべきことを表し、違反は不具合である。不変条件は次のとおり。

- 落ち着いた後、glazewmのモニター数がゲストOSのディスプレイ数と一致する。ただし全ディスプレイ消失中は1のまま。
- 落ち着いた後、glazewmが認識しているどのモニターも、表示中のワークスペースをちょうど1つ持つ。持たないモニターへウィンドウを移したりフォーカスしたりするコマンドは失敗する。
- 各ステップの後、glazewmとzebarのプロセスが生きており、glazewmが制限時間内にIPCの問い合わせに応答する。ゲストデーモンがゲスト内で測り、制限時間は負荷のステップが動いていない間だけ適用する。制限時間はシナリオごとに決め、既定は2秒。プロセスが生きているとは、ハーネスが配置した実行ファイルから動くプロセスがあることを指し、フルパスで比べる。glazewmが動いていないか応答しないときは、比べるモニター数がないので、この不変条件だけの違反とし、シナリオは次のステップに進む。IPCの問い合わせの間に終了したglazewmは、応答しないではなく、動いていないとみなす。
- メッセージを処理しなくなったウィンドウがあっても、glazewmは他のウィンドウを管理し続ける。これは、そのようなウィンドウがある間もほかの不変条件が成り立つことで判定する。つまり、glazewmが制限時間内にIPCに応答し、ほかのタイル状態のウィンドウがすべて作業領域に収まることである。メッセージを処理しないウィンドウは誰にも動かせないので、止めたウィンドウ自身は比べない。
- 落ち着いた後、glazewmは既に存在しないウィンドウを管理しておらず、管理しているウィンドウはすべてトップレベルウィンドウである。テスト用ウィンドウに限らず、glazewmが報告するすべてのウィンドウが対象である。ゲストデーモンが各ハンドルについてOSに問い合わせ、`WS_CHILD`スタイルを持つウィンドウを子ウィンドウとみなす。
- 落ち着いた後、OSから読んだタイル状態の各ウィンドウの実際の矩形が、属するモニターの作業領域に収まる。矩形は見えている枠で、見えないリサイズ用の縁は含まない。ハーネスはほかのウィンドウの矩形を読まないので、比べるのはテスト用ウィンドウだけとする。また、表示中でないワークスペースのウィンドウの位置はglazewmの隠し方が決めるので、表示中のワークスペースのものだけを比べる。
- 落ち着いた後、zebarの設定が対象とするモニターごとに、そのモニター上にバーのウィンドウがちょうど1つある。

ベースラインは、すべき振る舞いが決まっていない箇所でSUTが現在していることを固定し、逸脱は振る舞いの変化として人が判断する。
ベースラインは観測結果を正規化した形で比べる。モニターは位置と矩形で、ワークスペースは名前で、テスト用ウィンドウはゲストデーモンが付けた識別子で特定する。同じ実行を繰り返しても変わる値（コンテナのUUID、ウィンドウハンドル、時刻）は捨てる。
後でその振る舞いが仕様として決まったら、ベースラインを不変条件か、SUTのリポジトリのユニットテストに置き換える。

この2種類に分けたきっかけは`bind_to_monitor`である。glazewmはこれを、ワークスペースをモニターに「存在すれば」固定すると説明しており、存在しない場合の振る舞いは決まっていない。そのためシナリオはベースラインで扱う。番号は物理モニターの識別子ではなく、左から右、次に上から下に並べたモニターの中での位置である。glazewmがこの結び付けを適用するのはモニターが追加されたときで、削除や配置変更のときには適用しない。そのため、トポロジーを変えるシナリオのベースラインはトポロジーごとに記録する。

### ゲストデーモンが対話セッションの中で動く

ハーネスはホストのキーボードやマウスを使わない。ホストの入力を使うと開発者の作業を妨げ、並列実行もできなくなる。
ゲスト内でSSHやPowerShell Directから起動したプロセスは、対話デスクトップのないセッションで動く。そこで作ったウィンドウは表示されず、ディスプレイを問い合わせてもコンソールではなくそのセッションの値が返る。そのためゲストデーモンを対話セッションに常駐させ、ゲスト側の作業はそこで行う。SSHとPowerShell Directは、ファイルの転送とデーモンへの接続にだけ使う。

### トポロジーを変える手段はアダプターの中だけで扱う

モニターを追加・削除する手段は基盤ごとに違う。仮想GPUのマルチヘッド、ゲスト内の仮想ディスプレイドライバー、RDPクライアントのモニター構成などがある。
シナリオにはモニターの宣言だけを書き、手段は`DisplayController`の実装の中だけで扱う。
同じシナリオの判定が基盤によって分かれたら、その差自体を調査対象にする。

### SUTはホストでビルドする

ゲストにツールチェーンを入れるとスナップショットが肥大し、ビルド環境の差が判定に混ざる。
SUTはホストの`../glazewm`と`../zebar`から指定コミットでビルドし、成果物だけをゲストに渡す。渡すのはglazewmのバイナリと、zebarのバイナリ、そのフロントエンドのビルド結果、同梱リソースである。WebView2ランタイムと、glazewmのreleaseビルドがインポートするMicrosoft Visual C++再頒布可能パッケージ（`vcruntime140.dll`）は、ゲストイメージに入れておく。glazewmの設定は`GLAZEWM_CONFIG_PATH`で渡す。
