# 003: ベースラインの保存と比較

- 状態: Accepted

## 背景

ベースラインは、すべき振る舞いが決まっていない箇所で、SUTが現在していることを固定する（docs/PRD.jp.mdのFR-15）。以後の実行では、ベースラインから外れた箇所を、不変条件の違反とは別に報告する。その変化を受け入れるかどうかは人が判断し、受け入れたら記録し直す。

この論点では次の要因を考慮する。

- 逸脱は人が判断するので、記録された2つの状態の差として読める必要がある。また、記録し直しも、リポジトリへのほかの変更と同じようにレビューできる必要がある。
- SUTのチェックアウトとビルドは食い違うことがあるので、ベースラインは記録元のSUTのコミットを持つ必要がある。
- 逸脱と不変条件の違反は分けて報告するので、比較はテストフレームワークではなく、不変条件と並んでドメインモデルに置く。
- 観測する内容はハーネスとともに増える。テスト用ウィンドウ（FR-13）ができたら、ウィンドウが加わる。

## 決定

ベースラインを持つシナリオは、それぞれ1つのJSONファイルbaselines/<シナリオ>.jsonを持ち、リポジトリにコミットする。ファイルには、SUTのコミットと、起動時と各ステップの落ち着いた観測結果を正規化した形で持つ。落ち着かなかったステップは`null`にする。

記録する観測結果は、ゲストOSのディスプレイの矩形と、glazewmのモニターである。モニターごとに、矩形、作業領域、DPI、フォーカスと、その上のワークスペースの名前、表示中か、フォーカス、タイル方向を持つ。ディスプレイとモニターは位置の順に並べ、ワークスペースはglazewmの順のままにする。コンテナのID、ウィンドウハンドル、デバイス名は、同じ実行を繰り返しても変わるので記録しない。

実行結果とベースラインは、ドメインモデルがステップごとに比べ、異なるステップを返す。ファイルの形式は、ドメインの型とは別にアダプターで定める。読み手の知らないフィールドを持つファイルや、ステップ数がシナリオと異なるファイルは比べずに、記録し直す。

`VMTEST_RECORD=1`を付けた実行は、比べる代わりにファイルを記録する。このとき、SUTのコミットを`VMTEST_SUT_COMMIT`で指定する必要がある。

## 採らない案

| 案 | 理由 |
|---|---|
| insta（スナップショットテストのクレート） | 比較がテストのアサーションになるので、逸脱をドメインモデルの判定結果に不変条件の違反と並べて持てない。クレートとコマンドラインツールも1つずつ増える |
| YAMLなど別の形式で自前 | 構造はJSONと同じで依存が1つ増える。Rustでよく使われるYAMLのクレートは保守が終わっている |
| glazewmの応答全体から、実行ごとに変わる値を除いたもの | glazewmがフィールドを足すだけで逸脱になり、除く値の一覧をglazewmに合わせて保ち続ける必要がある |

## 結果

- シナリオのステップを変えると、そのベースラインは古くなり、記録し直す。
- 記録するフィールドの外にある振る舞い（例えば、DPIの値は変えずにDPIの扱いだけが変わる場合）は、それを表すフィールドを足すまで捉えられない。フィールドを足すと、すべてのベースラインが古くなる。
- 記録するときは、SUTのコミットを手で指定する。
