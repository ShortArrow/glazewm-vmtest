# 004: ゲストデーモンとテスト用ウィンドウのアプリケーションの間の通信方式

- 状態: Proposed

## 背景

ゲストデーモンは、テスト用ウィンドウのアプリケーションに、ウィンドウの生成、メッセージ処理の停止と再開、破棄を指示する（docs/ARCHITECTURE.jp.mdの「Adapters」）。アプリケーションはUIフレームワークごとに1つあり、それぞれそのフレームワーク本来の言語で書く。

この論点では次の要因を考慮する。

- どのフレームワークの言語でも、その通信方式を扱える必要がある。Rust、C#、JavaScript、Dart、Java、C++などである。
- デーモンはユーザーの整合性レベルで動くので、昇格したテスト用ウィンドウは`RunLevel Highest`のスケジュールタスクで起動する必要がある。そのとき、デーモンとアプリケーションの間にパイプはない。
- ランナーとデーモンの間は、すでに1行に1つのJSONで話している（ADR 002）。

## 決定

デーモンはアプリケーションごとにループバックのTCPポートを選んで待ち受け、そのアドレスを唯一の引数としてアプリケーションを起動する。アプリケーションはそこに接続し、1行に1つのJSONで書かれた指示を読み、指示ごとに1行で答える。指示と答えの型はプロトコルのクレートに含める。アプリケーションは接続が閉じると終了する。

## 採らない案

| 案 | 理由 |
|---|---|
| 子プロセスの標準入出力 | 昇格したアプリケーションのようにスケジュールタスクから起動したものには、デーモンへのパイプがない。そのため、権限の軸を扱うには2つ目の通信方式が要る |
| 名前付きパイプ | Dartなど、一部のフレームワークの言語の標準ライブラリには名前付きパイプのクライアントがなく、そのアプリケーションごとに個別の回避策が要る |

## 結果

- ポートには、ゲスト内のどのプロセスからも認証なしで接続できる。これはADR 002と同じ前提で受け入れる。指示は型付きで何も起動せず、ゲストに秘密を置かない。
- 起動から数秒以内に接続しないアプリケーションは、待ち続けずに要求の失敗として報告する。
