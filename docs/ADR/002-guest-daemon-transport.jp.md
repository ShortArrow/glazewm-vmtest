# 002: ランナーとゲストデーモンの間の通信方式

- 状態: Proposed

## 背景

ホストのランナーは、ゲストの対話セッションに常駐するゲストデーモンに、プロセスの起動、負荷の変更、トポロジー・ウィンドウの矩形・プロセスの生存の報告を頼む（docs/ARCHITECTURE.jp.mdの「Adapters」）。

この論点では次の要因を考慮する。

- 落ち着いた状態の判定では、各ステップの後にゲストを繰り返し問い合わせる。そのため、1回の要求にかかる時間が、落ち着いた状態をどれだけ細かく観測できるかを決める。
- 作業は対話セッションの中で行う必要がある。SSHから起動したプロセスはセッション0で動き、そのデスクトップが見えない。
- 同じ通信方式がどの基盤でも使える必要がある。dockur/windowsはコンテナのポートをホストの`127.0.0.1`に転送し、Hyper-VのゲストにはVMのネットワークで届く。
- glazewm自身のIPCはゲスト内のTCPサーバーで、ハーネスはすでにセッションをまたいでそこに届いている。

## 決定

ゲストデーモンはゲスト内のTCPポートで待ち受ける。ランナーは、基盤がホストの`127.0.0.1`に転送したポートから接続する。要求と応答はJSONで、1行に1オブジェクト。SSHとPowerShell Directは、ファイルの転送と、ログオン時にデーモンを起動する登録にだけ使う。

## 採らない案

| 案 | 理由 |
|---|---|
| 要求ごとにSSHでコマンドを送る | 要求のたびにSSHとPowerShellが起動するので、落ち着いた状態のポーリングには遅すぎる。セッション1で動かす要求のたびにスケジュールタスクも要る |
| 共有フォルダーに要求と応答のファイルを置く | 遅延が大きく、新しいファイルにすぐ気付く手段がない |

## 結果

- シナリオの開始前にデーモンが動いている必要がある。ランナーはスナップショットを復元するたびに、デーモンを待つ。
- デーモンはプロセスを起動でき、認証も持たないので、ポートは`127.0.0.1`にだけ公開する。要求は型で決まっており、コマンドラインや引数をそのまま渡す要求は持たない。そのまま渡せると、同じDockerネットワーク上の別のコンテナなど、ポートに届く誰でもゲスト内で任意のプログラムを実行できてしまう。
- 要求と応答の型は、ランナーとデーモンで1つのRustクレートとして共有する。
