# 005: Windowsゲストを動かす基盤

- 状態: Accepted

## 背景

ハーネスは、Windowsゲストをスナップショットに戻し、その中でシナリオを実行して観測する。これを何度も繰り返す（docs/PRD.jp.md）。

この論点では次の要因を考慮する。

- **自動化と保守の費用。** ハーネスが手間に見合うのは、人が見ていなくても動き続ける場合だけである。ハーネスを変えていないのに動かなくなりうる基盤は、そのたびに費用がかかる。
- **dockur/windowsにはKVMが要る。** dockur/windowsのコンテナは、WindowsをQEMUとKVMで動かす。Windowsホストでは、LinuxコンテナはWSL2の仮想マシンの中で動く。そのため、そこでのKVMはHyper-Vの中の入れ子の仮想化になる。
- **ハーネスを変えていないのに、入れ子の仮想化が使えなくなった。**
  - 2026-10-27に、ビルド26300.9711のWindows 11ホスト2台で次の状態になった。
    - WSL2のカーネルが`Hyper-V: Nested features: 0x0`を記録した。
    - `/dev/kvm`も`svm`フラグも現れなかった。
  - この状態は、次のどの条件でも変わらなかった。
    - `.wslconfig`で`nestedVirtualization=true`にしても。
    - WSL 2.6.3でも3.0.3でも。
    - メモリ整合性（HVCI）がオンでもオフでも。
  - 2台のうち1台では、2026-10-16に同じ構成でdockurのゲストが動いていた。WSLは警告を出さなかった。
- **Hyper-Vはゲストを1段目の仮想マシンとして動かす。** 入れ子の仮想化は要らない。Windows 11 Proのホストならどれにでもある。
- **モニターの増減はハイパーバイザーに依存しない。** ゲスト内のIddCx仮想ディスプレイドライバで行う（docs/spikes/2026-10-07-iddcx-virtual-display-driver.md）。Hyper-Vの合成ビデオは出力が1つしかないので、このドライバがモニターごとに増減できる唯一の手段になる（docs/ROADMAP.jp.md）。
- **dockurのアダプタとシナリオはあるが、Hyper-Vのアダプタはない。** docs/ROADMAP.jp.mdには、Hyper-V向けのスパイクが3つ残っている。「スナップショットの種類」「ゲスト画面のキャプチャ」「WMIによるHyper-Vの操作」である。

## 決定

Windowsゲストは、ハーネス専用のWindows 11 ProホストのHyper-Vで動かす。Hyper-Vのアダプタはdockurのアダプタと同じポートを実装する。そのため、シナリオは変えない。dockurのアダプタは、KVMのあるLinuxホスト向けに残す。

## 採らない案

| 案 | 理由 |
|---|---|
| Windowsホストでdockur/windows | WSL2の仮想マシン内の入れ子の仮想化に依存する。2台のホストで起きたように、これはホストの更新で警告なく使えなくなりうる |
| KVMのあるLinuxホストでdockur/windows | 入れ子の仮想化もハーネスの変更も要らない。しかし、Windows 11ゲストに足りるメモリとディスクを持つLinuxホストがない |
| WindowsホストでWindows Hypervisor Platform（WHPX）を使うQEMU | 入れ子の仮想化は要らず、qcow2のスナップショットと`screendump`もそのまま使える。しかし、Windows 11ゲストがその上で安定して動くかはわからない。また、dockurが提供している無人インストールを作り直す必要がある |
| ホストのメモリ整合性（HVCI）をオフにする | 入れ子の仮想化は戻らなかった |

## 結果

- 背景に挙げたHyper-Vの3つのスパイクを終えるまで、この基盤でのフェーズ1には進めない。docs/ROADMAP.jp.mdでは、フェーズ1と2でHyper-Vとdockur/windowsが入れ替わる。
- ゲストイメージは、dockurの無人インストールを使わずに作る。docs/GUEST-IMAGE.jp.mdの手順はHyper-V向けに書き直す。
- ランナーをどこで動かすかは、Hyper-Vのアダプタと一緒に決める。候補は、Hyper-Vのホスト上と、そのホストを遠隔で制御する別のマシンである。
- docs/PRD.jp.mdのうちDocker Desktopと入れ子の仮想化を挙げている制約は、Hyper-Vを挙げるように変わる。
