# 001: 実装言語

- 状態: Accepted

## 背景

この決定が対象とするのは、ホスト側のランナーとゲストデーモン。テスト用ウィンドウは、UIフレームワークごとにそのフレームワーク本来の言語で書いた別のアプリケーションが作る（docs/ARCHITECTURE.jp.mdの「Adapters」）。そのため、ここでの選択が全種類のウィンドウを賄う必要はない。

ランナーはドメインモデル（`Topology`、`Scenario`、`Invariant`、`Baseline`）を持ち、シナリオを実行し、Hyper-V、Docker（dockur/windows）、RDP/VNCクライアントのアダプターを含む。ドメインを表せる型システムと、テスト駆動に使えるユニットテストの仕組みが要る。
ゲストデーモンはゲストの対話セッションで動き、CPU/メモリ/GPUの負荷を発生させ、SUTとテスト用ウィンドウのアプリケーションを起動し、トポロジー、ウィンドウの矩形、プロセスの生存を読み取る。

この論点では次の要因を考慮する。

- glazewmとzebarはRustで書かれており、コントリビュータもRustで作業している。
- glazewmのIPCメッセージは`wm-common`クレートで定義されている。
- Hyper-VはPowerShellのコマンドレットかWMI（`Msvm_*`クラス）で操作する。RustからはCOM経由でWMIを使う。.NETならHyper-VのPowerShellモジュールをプロセス内でホストすることもできる。

## 決定

ランナーとゲストデーモンの両方をRustで書く。Hyper-VはRustからWMIで操作する。WMIで賄えない操作はHyper-Vアダプターの中に限り、Hyper-VのPowerShellモジュールを子プロセスで呼ぶ。

## 採らない案

| 案 | 理由 |
|---|---|
| C# | Hyper-Vの操作は最も楽だが、ランナーに手を入れるglazewmとzebarのコントリビュータに2つ目のツールチェーンを求める。WinForms、WPF、WinUI 3のウィンドウを作れることはこの決定に関係しない。それらのウィンドウは別のテスト用ウィンドウのアプリケーションが作るためである |
| PowerShell | Hyper-Vの操作は最も直接的だが、型付きのドメインモデルとテスト駆動に向かない。単発のスクリプトには引き続き使える |

## 結果

- ランナーとゲストデーモンは、glazewm、zebarとツールチェーンを共有する。テスト用ウィンドウのアプリケーションはそれぞれのツールチェーンを持ち込むが、ゲストイメージに1度だけビルドして入れ、実行のたびにはビルドしない。
- ランナーは`wm-common`に依存せず、未知のフィールドがあっても読める独自の型でglazewmのIPCのJSONを読む。これにより、IPCスキーマが最新と異なる古いSUTのコミットも観測できる。
- WMIでHyper-Vの操作がどこまで賄えるかは段階0の検証項目にする。足りない部分はHyper-Vアダプターの中だけで扱う。
