# スパイク: 動いているゲストを戻せるHyper-Vチェックポイントの種類

- 日付: 2026-10-31
- スパイク: docs/ROADMAP.jp.mdの「スナップショットの種類」
- ホストとゲスト: docs/spikes/2026-10-31-hyperv-wmi-control.jp.mdと同じ。時刻の同期の統合サービスはオン

## 方法

チェックポイントの種類ごとに、標準と運用（`-CheckpointType ProductionOnly`）で次を行った。

1. `daemon-task`に戻してゲストを起動し、セッション1で`explorer.exe`が動くのを待ってから、ゲストデーモンをコピーしてタスク`vmtest-guest-daemon`を起動する。
2. 動いているゲストのチェックポイントを取る。
3. 90秒待ち、ゲストデーモンを止めて、ゲストの電源を切る。
4. チェックポイントに戻してゲストを起動し、SSHで次を調べる。ゲストデーモン、セッション1の`explorer.exe`、有効なモニター（`WmiMonitorBasicDisplayParams`）、起動時刻、ゲストの時計。

ゲストの時計は、SSHを実行したマシンの時計と、各SSH呼び出しの中間時点で比べた。呼び出しにかかった時間は測っていない。チェックポイントを取る前の差はどちらも+5.5秒で、これは2台のマシンの間のずれであり、復元によるものではない。

## 観察

| | 標準 | 運用 |
|---|---|---|
| 復元直後の状態 | Saved | Off |
| 起動からSSHが応答するまで | 3.9秒 | 12.1秒 |
| ゲストデーモン | 電源断の前に止めたのに、セッション1で動いていて`127.0.0.1:7041`で待ち受けていた | 動いていない |
| セッション1の`explorer.exe` | 動いている | 動いている（自動ログオン） |
| 起動時刻 | 変わらない。ゲストは再開した | 新しい。ゲストは起動し直した |
| 有効なモニター | 2台で、前と同じ | 2台で、前と同じ |
| 時計の差（3.9秒／12.1秒から起動後60秒まで） | +3.2〜+4.1秒 | +5.6〜+5.9秒 |

標準チェックポイントは、復元の90秒前のゲストを保存していた。それでも、SSHが応答した時点で時計の差はチェックポイント前の値から2.3秒以内だった。90秒の遅れは見られなかった。

## 設計への影響

- ログオン済みでゲストデーモンが動いた状態に戻るのは、動いているゲストの標準チェックポイントだけである。運用チェックポイントは電源の切れたゲストに戻る。ゲストは起動して自動ログオンするが、タスクをもう一度起動するまでゲストデーモンは動かない。
- 動いているゲストの標準チェックポイントに戻すと、起動の時間を省ける。SSHは11〜12秒ではなく3.9秒で応答した。ただし、そのチェックポイントの中のゲストデーモンは、取ったときに動いていた実行ファイルである。ゲストデーモンを含んだまま動いているチェックポイントは、ゲストデーモンが変わるたびに取り直す必要がある。一方、電源を切ったチェックポイントなら、実行のたびにコピーしたゲストデーモンをそのまま使える。
- SSHが応答した時点で、ゲストの時計に90秒の遅れは残っていなかった。それを直したのが時刻の同期なのかは試していない。

## 測っていないこと

- 数秒より細かい時計の精度と、時刻の同期をオフにしたときの時計。
- 有効なモニターの数以外の画面の状態。配置、解像度、復元でゲスト内に画面変更のメッセージが届くかどうか。
- RDPのセッションがコンソールを持っているときに、動いているチェックポイントへ戻すこと。
