# PRD: glazewm-vmtest

## 目的

glazewmとzebarの、ディスプレイ構成の変化に関わる不具合を、物理ハードウェアなしで再現・検出できるようにする。

この種の不具合はモニターの抜き差しやRDPの切断といった手作業で起こすため、再現手順が特定の人と機材に依存する。
ハーネスはその手作業を仮想化基盤の操作に置き換え、同じ初期状態から同じ手順を何度でも実行できるようにする。

## 利用者

- glazewm/zebarのコントリビュータ。不具合を再現するシナリオを書き、修正前にfail、修正後にpassすることを確かめる。
- AIコーディングエージェント。開発者の画面とキーボードを奪わずに、上記と同じことをする。

## 用語

| 用語 | 意味 |
|---|---|
| SUT | 検証対象。glazewmとzebarを特定のコミットからビルドしたもの |
| ゲスト | SUTを動かす仮想マシン、またはコンテナ内の仮想マシン |
| ゲストデーモン | ゲストの対話デスクトップセッションに常駐し、ハーネスに代わってSUTとテスト用ウィンドウを起動し、ゲストを観測するプログラム |
| スナップショット | 毎回の実行の起点にする、保存したゲストの状態（Hyper-Vの用語ではチェックポイント） |
| トポロジー | ゲストOSから見えるディスプレイの集合。ディスプレイごとに識別子、矩形、作業領域、DPI、プライマリかどうかを持つ |
| 落ち着いた状態 | 待機時間のあいだ、トポロジー、ウィンドウの集合、glazewmのIPCイベントのどれにも変化がない状態 |
| シナリオ | Given（初期トポロジーとSUTの設定）、When（トポロジー、セッション、負荷、ウィンドウを変える操作の列）、Then（不変条件とベースライン）の組 |
| 不変条件 | SUTが何をすべきかに関わらず成り立つべき条件。違反は不具合 |
| ベースライン | 期待する振る舞いが決まっていない箇所について、基準実行で記録したSUTの振る舞い。逸脱は振る舞いの変化で、人が判断する |

## ユースケース

| ID | 契機 | 例 |
|---|---|---|
| UC-1 | モニターの追加・削除 | 1枚 → 3枚 → 2枚。中央のモニターだけを外す |
| UC-2 | ディスプレイ設定の変更 | 解像度、スケーリング、配置、プライマリ |
| UC-3 | RDPセッションの変化 | 接続、切断、モニター数や解像度が異なるクライアントからの再接続 |
| UC-4 | VNCクライアントの変化 | 接続と切断。ゲストのトポロジーが変わら*ない*ことも検証対象 |
| UC-5 | 電源・セッション状態の変化 | スリープからの復帰、ロックとアンロック |
| UC-6 | 全ディスプレイの消失と復帰 | 全モニターを外してから1枚追加する |
| UC-7 | 設定が前提とするモニター構成と実際の構成の不一致 | モニター1枚の環境で、glazewmの`bind_to_monitor`が3枚目のモニターを指す設定のまま起動・設定再読み込みする。zebarの`monitorSelection`が、型`index`や`name`で存在しないモニターを指す |
| UC-8 | ゲストのリソース枯渇 | トポロジー変化の前や最中にCPU、メモリ、GPUが飽和している |
| UC-9 | 応答しないウィンドウ | glazewmが移動・リサイズ・非表示にしようとしているウィンドウがメッセージを処理しなくなる。トポロジー変化をまたぐ場合を含む |
| UC-10 | ウィンドウの大量発生と短命なウィンドウ | 多数のウィンドウを短時間に生成・破棄する。生成から数ミリ秒で、glazewmが処理し終える前に破棄・非表示になるウィンドウやダイアログ。単独で、またはトポロジー変化と重ねて |
| UC-11 | ウィンドウの種類 | 下記「ウィンドウの種類」の各種類を、トポロジー変化をまたいで管理する |
| UC-12 | 組み合わせと反復 | 操作列の無作為生成、長時間の繰り返し |

| FR-2 | 実行のたびにゲストを同じスナップショットから復元する | 全て |
| FR-3 | 指定したコミットのSUTをホストでビルドしてゲストに配置し、Givenのトポロジーと設定がそろってから、ゲストの対話セッションで起動する | 全て |
| FR-4 | ゲストのトポロジーをモニター単位で追加・削除・変更できる | UC-1, UC-2, UC-6 |
| FR-5 | RDP/VNCクライアントの接続と切断をホストから操作できる | UC-3, UC-4 |
| FR-6 | スリープ、復帰、ロック、アンロックをホストから起こせる | UC-5 |
| FR-7 | 各ステップが落ち着いた後、ゲストの対話セッションから、トポロジー、全ウィンドウの実際の矩形、glazewmの状態（`glazewm query`の出力）、zebarのウィンドウ配置を取得する | 全て |
| FR-8 | オラクルが不変条件を判定し、失敗したステップと差分を報告する | 全て |
| FR-9 | 実行ごとにSUTのログ、状態ダンプ、スクリーンショットを成果物として保存する | 全て |
| FR-10 | 失敗したシナリオを、記録した操作列からそのまま再実行できる | UC-12 |
| FR-11 | GivenでSUTの設定（glazewmの設定、zebarのウィジェットパック）を初期トポロジーとは独立に指定でき、ステップで差し替えて再読み込みできる | UC-7 |
| FR-12 | ゲストのCPU、メモリ、GPUの負荷を、強さを指定してステップとして開始・停止できる | UC-8 |
| FR-13 | ゲスト内にテスト用ウィンドウをステップとして生成できる。種類の指定、指定期間内に指定数の生成、メッセージ処理の停止と再開を含む | UC-9, UC-10, UC-11 |
| FR-14 | 毎回の観測で、glazewmとzebarのプロセスが生きているか、glazewmがゲスト内で測った制限時間内にIPCの問い合わせに応答するかを記録する | UC-8, UC-9, UC-10 |
| FR-15 | シナリオは観測結果をベースラインとして記録できる。以後の実行では、ベースラインからの逸脱を不変条件の違反とは区別して報告する | 全て |
| FR-16 | シードから操作列を無作為に生成でき、シナリオを指定の回数または時間だけ繰り返せる | UC-12 |
| FR-17 | 制限時間内に落ち着かなかったステップは、passではなく「落ち着かなかった」として報告する | 全て |

## ウィンドウの種類

ウィンドウは互いに独立な軸で異なり、シナリオは軸ごとに値を1つ指定する。網羅は軸ごとと、軸の2つ組ごとに判定する。

| 軸 | 値 |
|---|---|
| UIフレームワーク | Win32、.NET（WinForms、WPF、WinUI 3、Avalonia）、UWP（`ApplicationFrameHost`がホスト）、Web系（Electron、Tauri/WebView2）、Rustネイティブ（winit、egui、gpui）、Qt、GTK、Flutter、Java（Swing）、ゲーム系（SDL、GLFW）、コンソール（conhost、Windows Terminal） |
| DPI認識 | 非対応、システムDPI、モニターごと、モニターごとv2 |
| 権限 | glazewmと同じ整合性レベル、昇格（管理者） |
| 関係 | 所有者のないトップレベル、所有されたモードレスウィンドウ（ツールパレット、検索ダイアログ）、所有されたモーダルダイアログ（メッセージボックス、コモンダイアログを含む）、ポップアップ（メニュー、ツールチップ、通知）、子ウィンドウ（`WS_CHILD`、MDI子ウィンドウ） |
| 存続時間 | 持続する、短命（生成から数ミリ秒で破棄）、表示から数ミリ秒で非表示、表示と非表示を繰り返す |
| スタイル | 通常、枠なし、ツールウィンドウ、レイヤード/透過、最前面、最小/最大サイズの制約付き |
| 状態 | 通常、最小化、最大化、全画面（枠なし）、排他的全画面（DirectX） |
| 応答性 | 応答する、メッセージを処理しない |

## 作業の順序

回帰テストを先に固める。振る舞いを仕様として決める前に、glazewmとzebarの現在の振る舞いをベースラインとして記録し、意図したかどうかに関わらず振る舞いの変化に気付けるようにする。期待する振る舞いを決めてテスト駆動で修正するのはその後で、ベースラインができたユースケースから1つずつ進める。

## 非機能要件

- 隔離: ハーネスは開発者のデスクトップセッションに入力を送らない。ゲスト内では、ゲストデーモンがゲスト自身の対話セッションの中で動く。
- ヘッドレス: ゲストの画面をホストのウィンドウで開かずに実行できる。
- 再現性: 同じシナリオ、SUT、スナップショットからは同じ操作列が実行される。実行ごとに判定が変わる場合は不安定（flaky）として報告し、原因をSUTとハーネスのどちらとも決めつけない。

## 非ゴール

- glazewm/zebarのユニットテストの置き換え。ハーネスが見つけた不具合の回帰テストは、可能な限り各リポジトリのユニットテストとして書く。
- 不具合の修正。修正は各リポジトリで行う。
- 性能の測定。
- 実在のGPUドライバーやモニター固有の不具合の再現。

## 制約

- Windowsゲストは、ハーネス専用のWindows 11 ProホストのHyper-Vで動かす（docs/ADR/005-windows-guest-platform.jp.md）。
- dockur/windowsはKVMを必要とするので、KVMのあるLinuxホストで動かす。WindowsホストではWSL2の入れ子仮想化に依存することになる。
- ゲスト内のSUTは、自動ログオンするユーザーの対話デスクトップセッションで動かす。SSHやPowerShell Directから起動したプロセスは、そのデスクトップを持たない非対話セッションで動く。
- macOSゲストはApple SiliconのMacホスト上で、Virtualization.frameworkを使ってしか動かせず、そのホストは手元にない。macOSの使用許諾契約が仮想マシンでの実行を認めるのは、macOSが動いているApple製ハードウェア上で、1台につき追加2コピーまで、ソフトウェア開発やテストなどの目的に限られる。Virtualization.frameworkも同じく2つまでに制限している。
- Windowsゲストには評価版か、利用者が保有するライセンスを使う。

## 受け入れ基準

- glazewmまたはzebarの既知のディスプレイ関連不具合を1件以上シナリオとして書け、修正前のコミットでfail、修正後のコミットでpassする。
- 同じシナリオを同じSUTで10回連続実行し、判定結果がすべて一致し、「落ち着かなかった」と報告された実行がない。
- 各ベースラインのシナリオを、そのシナリオが扱う範囲で振る舞いを変えたSUTのコミットに対して実行すると、逸脱が報告される。
